# EVS-3 -- Main-thread Wakeup

Status: **contract frozen before implementation** (same rule as every
phase).  North Star framing: EVS-2's A/B closure proved the measured
~20ms submit->committed floor is harness/polling latency, not system
latency; it dominates every small-document scenario.  EVS-3 removes
that floor so that the NEXT real bottleneck becomes measurable.

## 0. Goal (North Star form)

> When a background result is already ready, the main thread learns
> about it within microseconds instead of on the next poll tick --
> WITHOUT letting workers touch Emacs state.

Success is user-path shaped:

```
keypress -> ... -> worker done -> [wake] -> commit -> visible
                                  ^
                                  sub-ms instead of ~20ms
```

NOT "wakeup benchmark goes up".  EVS-3 changes NOTHING about task
semantics, admission, snapshot or storage.

## 1. Explicit non-goals

- No multi-threaded Emacs UI redesign.
- Workers never call Elisp, never touch buffers/GC/locks (#ARCH 1-3).
- No scheduler API that understands Emacs (`scheduler_wakeup_main()`
  is banned).  The primitive expresses ONLY "new main-thread work
  exists"; how it is consumed (timer / event loop / input event /
  safe point / batch condvar) belongs to the integration layer.
- No queue redesign: the existing result FIFO stays; only
  notification state is added.

## 2. Architecture placement

```
Emacs integration layer (enca-evs / future safe-point bridge)
        |  supplies the sink, consumes the signal
        v
enca_wake_source          <-- Runtime Notification primitive
        ^  notify()
        |
P3 scheduler result funnel (one optional observer hook)
```

The scheduler receives an OPTIONAL, business-ignorant observer:
`void (*result_notify)(void *ctx)`.  It does not know or care what
the function does.  Requirement on the sink: LEAF-SAFE -- it must not
acquire any ENCA scheduler/snapshot lock and must not touch Emacs
state (it runs on worker threads).

## 3. Notification protocol (strict, coalescing)

States (per consumer cycle), implemented as one token under a mutex
+ condvar -- the MUTEX is what makes this a protocol rather than an
atomic flag:

```
IDLE        token == 0            nothing outstanding
NOTIFIED    token == 1            a wake is pending
MAIN_DRAINING   implicit          wait() returned true, consumer is
                                  draining; a notify arriving here sets
                                  NOTIFIED again -> the next wait()
                                  returns immediately (no lost wakeup)
```

Producer rule: enqueue result FIRST, then notify.  Consumer rule:
drain until poll returns 0, THEN enter wait(); wait() re-checks the
token UNDER THE MUTEX before sleeping.

Lost-wakeup argument: if produce+notify completes before the
consumer's final empty-poll, the poll sees the result (no wait).
Otherwise notify strictly follows the last empty-poll, so either it
lands before wait() takes the mutex (token==1 -> immediate return)
or after (signal wakes the sleeper).  No third interleaving exists.

Storm rule: N producers notifying between drains collapse into AT
MOST ONE real wakeup per drain cycle (token coalescing); the drain
loop empties the whole FIFO per wake.

## 4. Shutdown / lifetime rules

- The sink may be destroyed only when no thread is inside wait().
  Standard order: shutdown workers -> join -> last drain -> destroy.
- After STOP_ACCEPTING no new notifications are generated by submits;
  results produced by the shutdown drain still notify (the consumer
  must be able to see them).
- Restart = fresh init of scheduler + source (no hidden carryover);
  generation resets are ordinary staleness, notifications behave
  identically for DROP records (commit callback filters them).

## 5. Correctness gates BEFORE performance (EVS-3.0)

Required suites (test_wake.c):

```
wake/single              one notify -> exactly one wait hit
wake/burst               M notifies coalesce to <=M hits, >=1
wake/producer-storm      P threads x K notifies; consumer keeps
                         draining until quiescent; zero lost results
wake/drain-race          producer enqueues inside the consumer's
                         empty-poll -> wait window: no lost wakeup
wake/notify-during-drain notification arriving while MAIN_DRAINING
                         makes the next wait return immediately
wake/shutdown            shutdown ordering; post-shutdown submits
                         generate no notifications; no use-after-
                         destroy; accounting identity holds
wake/generation-reset    generation bump mid-stream: stale drops are
                         notified + filtered; identities intact
```

Hard invariant: `results_enqueued > 0 => eventually drained > 0`
(verified by counting, not timing).  ASan clean REQUIRED; TSan clean
REQUIRED (Linux/WSL gcc; the Windows toolchain cannot run TSan --
recorded in EVS2-DECISION.md section 6).

## 6. Performance gate (EVS-3.1, only after section 5 is green)

Re-run E1/E3/E4 through the SAME batch harness with the wait side now
blocking on the wake source instead of sleep-for polling:

```
floor target: p50 submit->committed << 20ms (sub-ms ideal)
A/B rerun (final EVS-2 word):
  A = full capture + full analysis
  B = incremental capture + full analysis
  with NO polling floor.  If A ~= B still holds, EVS-2's NO-GO is
  confirmed under fair conditions and becomes permanent.
```

## 7. Stop conditions

- If wakeup lands but E1/E3/E4 tails stay flat AND capture arms stay
  equal, the next lever is chosen by measurement (GUI redisplay vs
  Real Completion) -- NOT by preference.
- Range Snapshot / Region View remains BANNED until Real Completion
  measurements show Full Snapshot is the actual bottleneck
  (demand -> evidence -> API, never API -> imagined workload).

## 8. Outcome (2026-08-24): LANDED

Correctness gates (section 5): all seven suites green, 24318/0 native
x3, ASan clean, TSan (WSL gcc) 0 warnings / 24315 / 0 -- closing the
TSan evidence gap inherited from EVS-2 for the whole scheduler+wake
concurrency surface.

Found and fixed during the gates: the documented STOP_ACCEPTING
submission gate was never enforced in enca_sched_submit (the
shutdown_rejects counter existed but nothing incremented it; a
post-shutdown submit silently queued).  Fixed with a lifecycle check;
covered by wake/shutdown.

Performance (EVS-3.1, real Emacs build, same A/B harness):

```
submit->committed p50        before floor     after wakeup
E1 idle typing   full arm    ~19.3ms          0.083ms
E1 idle typing   incr arm    ~19.5ms          0.0008ms
E4 1MB           both arms   ~17-20ms         4.3-6.2ms
E4 10MB          full/incr   ~51-76/54-60ms   43-76 / 37-42ms
E4 100MB         full/incr   ~452/~485ms      ~386-624 / ~438-497ms
```

The ~20ms measurement floor is gone (down to microseconds).  With a
fair view of capture costs: incremental now wins visibly at 10MB
(~40 vs ~55ms median) and ties at 100MB where the synthetic
full-document analysis dominates by design.  Verdict per section 6:
EVS-2's NO-GO on storage STANDS; the user-path lever this phase
targeted was the floor itself.  Next decision (Completion vs
Redisplay) is now measurable without harness pollution.
